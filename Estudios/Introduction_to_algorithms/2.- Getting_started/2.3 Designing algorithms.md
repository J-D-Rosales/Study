# 2.3.1 The divide-and-conquer approach
Many useful algorithms are **recursive** in structure.
These algorithms typically follow a **divide-and-conquer** approach: they break the problem into several subproblems that are similar to the original problem but smaller in size, solve the subproblems recursively, and then combine these solutions to create a solution to the original problem.
<span style="color:	#87CEEB">Three steps</span>:
- **Divide** the problem into a number of subproblems that are smaller instances of the same problem.
- **Conquer** the subproblems by solving them recursively. If the subproblem sizes are small enough , however, just solve the subproblems in a straightforward manner.
- **Combine** the solutions to the subproblems into the solution for the original problem.
We'll use the **merge sort** algorithm to solve this problem.
The steps would be the next:
- **Divide:** Divide the n-element sequence to be sorted into two subsequences of $\frac{n}{2}$ elements each
- **Conquer:** Sort the two subsequences recursively using merge sort.
- **Combine:** Merge the two sorted subsequences to produce the sorted answer.
The key operation is in combine, indeed, merging of two sorted sequences. We use an auxiliary procedure MERGE(A,p,q,r), where $A$ is an array and $p,q$, and $r$ are indices into the array such that $p\leq q<r$.
It is assumed by the procedure that the subarrays $A[p..q]$ and $A[q+1..r]$ are in sorted order. It **merges** them to form a single sorted subarray that replaces the current subarray $A[p..r]$.
**Order of growth:** $\Theta(n)$ 
where $n = r-p + 1$ is the total number of elements being merged.
The algorithm is as follows.
We have three piles. One of them is face down (is the larger). And the other two are face up. 
The two that are face up, we want to make it like the larger. Since, they are in order we do as follow. We choose the smaller of the two cards on top of the face up piles, removing it from its pile (which exposes a new top card), and placing this card face down onto the output pile.
Since we perform at most $n$ basic steps, merging takes $\Theta(n)$ time.
The next pseudoalgorithm do that, but with a sentinel card at each pile, which contains a special value in this case $\infty$. Whenever a sentinel is exposed , there is nothing smaller than that. Since we know in advance that exactly $r-p + 1$ cards will be places onto the output pile, we can stop once we have performed that many basic steps.

# 2.3.2 Analyzing divide-and-conquer algorithms
When an algorithm contains a recursive call to itself, we can often describe its running time by a **recurrence equation** or **recurrence**, which describes the overall running time on a problem of size $n$ in terms of the running time on smaller inputs. (You should know how to solve the recurrence, with mathematical tools to make it iterative.
A recurrence for the running time of a divide-and-conquer algorithm falls out from the three steps of the basic paradigm. As before, we let $T(n)$ be the running time on a problem of size $n$. If the problem size is small enough, say $n\leq c$ for some constant $c$, the straightforward solution takes constant time, which we write as $\Theta(1)$. 
Take attention, suppose that our division of the problem yields $a$ subproblems, each of which is $\frac{1}{b}$ the size of the original. (For merge sort, both $a$ and $b$ are 2, but is not always the case, $a \not= b$). It takes time $T\left( \frac{n}{b} \right)$ to solve one subproblem of size $\frac{n}{b}$, and so it takes time $aT\left( \frac{n}{b} \right)$ to solve $a$ of them. If we take $D(n)$ time to divide the problem into subproblems and $C(n)$ time to combine the solutions to the subproblems into the solution to the original problem, we get the recurrence
$$
T(n) = \begin{cases} 
\Theta(1) & \text{if } n \leq c, \\
aT(n/b) + D(n) + C(n) & \text{otherwise}.
\end{cases}
$$
## Analysis of merge sort
If we assume that the original problem size is a power of 2, this does not affect the order of growth to the recurrence.
Setting the recurrence for $T(n)$. the worst-case running time of merge sort on $n$ numbers. When it's not 1 element:
**Divide**: The divide step just computes the middle of the subarray which takes constant time. $D(n) = \Theta(1)$.
**Conquer**: We recursively solve two subproblems, each of size $\frac{n}{2}$, which contributes $2T\left( \frac{n}{2} \right)$ to the running time.
**Combine:** We've have already noted that the MERGE procedure on an $n-element$ subarray takes time $\Theta(n)$, and so $C(n) = \Theta(n)$.}
When we add $D(n)$ and $C(n)$ for the merge sort, we have $\Theta(n)$.
But, this is not the complete time. The master theorem (we'll see this later) states that $T(n)$ is $\Theta(n \lg n)$ where $lg$ stands for $\log_{2}n$. This is far better when the input is larger, since it growths logaritmically.
